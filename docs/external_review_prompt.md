## 프롬프트

```
너는 추천 시스템의 점수 설계를 검토하는 시니어 엔지니어다. 내 프로젝트의 점수 메커니즘을
비판적으로 검토해달라. 첨부한 as-is 문서와 소스가 근거다. 추측하지 말고 코드에서 확인한 것만
말해달라. 내가 이미 찾은 결함 목록(code_review 문서)이 있는데, 그중 틀린 지적이 있으면
그것부터 지적해주면 좋겠다 — 오늘 내가 두 번 잘못 판단한 적이 있어서 검증이 더 중요하다.

[서비스 정체성]
Hidden Gem — 한국 인디게임 추천. 핵심 가치는 "인지도는 낮지만 좋은 게임 발굴".
스팀 인기순위가 못 잡는 영역을 노린다. 1인 개발, 운영 비용에 민감(월 $15 내외 목표).
게임 12,843개를 LLM으로 49개 지표 + 9개 불리언으로 데이터화했다.

[확정된 설계 의도 — 이건 바꿀 대상이 아니다]
1. 점수는 사용자의 취향 입력 혹은 검색 문장(단어/문장/문단 모두)에 따라 달라져야 한다.
   같은 게임이 "힐링 원함"과 "공포 원함"에서 다른 점수를 받는 것이 정상이다.
   이걸 부정하는 방향의 제안(고정 품질 점수로 바꾸자 등)은 필요 없다.
2. 데이터는 지우지 않는다. 품질이 의심되는 게임도 분석 결과는 보존하고 노출만 제어한다.
3. 유명작이 상위에 오는 것은 정체성 위반이다. 다만 사용자가 명시적으로 검색한 경우는 예외.

[현재 상황 요약]
- 점수 경로가 두 개다. 취향 분석/Vibe칩은 score_v6(Core 75 + X-Factor 18 + Gem 6),
  유사 게임/문장 검색은 recommender((지표 60% + 임베딩 40%) x 94 + Gem x 5).
- 데이터가 두 코호트다. 교사 GPT-5.4로 만든 4,190개(인기작 위주)와 학생 gpt-5.4-mini +
  few-shot 12개로 만든 8,653개(최근 6개월 출시작 전수).
- 학생의 49지표는 교사 대비 평균 MAE 0.77(0~10 스케일)로 쓸 수 있는 수준이다. 단 3개
  (modding_support r=0.42, community_dependency r=0.61, monetization_fairness r=0.36)는
  신뢰 불가이고, 이 3개가 49차원 제곱오차의 25%를 차지한다.
- 학생의 gem_potential(LLM이 매긴 "숨은 명작 지수")은 교사 스케일로 환산 불가다
  (MAE 19.5, 스피어만 0.49, 편향 -18.4). 선형 보정을 적합하면 기울기 0.33이 나와
  8,456건이 σ16 → σ5로 압축되는 퇴화 매핑이 된다. 원인은 모델이 아니라 검증 데이터의
  범위 제한이다 — 교사가 채점한 게임은 gem 40~95에 몰려 있고 무명작 구간에 기준이 없다.
- 그래서 gem을 LLM 추정이 아니라 Steam 리뷰 실측으로 바꾸려 한다:
  100 x Wilson하한(긍정비율) x 무명도(1 - log1p(리뷰수)/log1p(20000))^0.5, 무명도 하한 리뷰 50.
  실측 최대값이 약 72다.
- 교사 4,190개는 review_count / steam_positive_ratio 가 비어 있다(수집 당시 저장 안 함).
  이 때문에 유명작 필터(max_review_count)가 NULL을 통과시켜 한 번도 작동한 적이 없다.

[내가 답을 원하는 것]
A. as-is 문서 12장의 D-1 ~ D-14 중 (1) 사실과 다른 것 (2) 심각도를 잘못 매긴 것
   (3) 내가 놓친 것을 찾아달라. 각각 file:line 근거를 달아달라.

B. 우선순위. 1인 개발자가 하루에 처리할 수 있는 양은 3~4개다. D 항목들을
   "추천 품질에 실제로 미치는 영향 / 수정 비용 / 되돌리기 난이도" 세 축으로 정렬해달라.

C. 구조적 판단 세 개:
   1. 점수 경로 두 개(score_v6 / recommender)를 하나로 합쳐야 하나, 용도가 달라 분리가
      맞나? 합친다면 어느 쪽을 기준으로 하고 무엇을 버려야 하나?
   2. 쿼리 의존성 구현이 두 가지 있다 — recommender의 4단계 가중치(5.0/2.0/0.5/0.1, 49지표
      전부에 적용)와 score_v6의 방식(장르 핵심 2~3개 + 사용자가 7 이상으로 준 지표만,
      가중치 2.0/1.0). 후자는 비교 지표 수가 적어 변별력이 어떨지 걱정된다. 어느 쪽이
      "취향에 따라 점수가 달라진다"는 목표에 더 맞나? 근거를 지표 개수·거리 분포 관점에서
      설명해달라.
   3. gem을 리뷰 실측으로 바꾸는 방향 자체가 타당한가? 리뷰가 아직 없는 신작(출시 직후)은
      구조적으로 히든젬 점수를 받을 수 없게 되는데, 발견 서비스로서 이건 받아들일 수 있는
      트레이드오프인가? 대안이 있나?

D. 정량 검증 방법. 지금은 "적용 전후로 고정 시나리오 13개의 상위 10위를 저장해 비교"하는
   회귀 스냅샷만 있다. 정답 라벨이 없는 상태에서 추천 품질 변화를 판단할 더 나은 방법이 있나?
   (행동 로그는 수집 구조만 있고 트래픽이 없어 데이터가 없다)

[제약]
```
