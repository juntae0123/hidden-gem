## 2. gem_potential을 보정으로 살릴 수 없는 이유 (시도했고, 거부했다)

선형 보정을 적합하면 기울기 **0.33**. 신작 8,456건에 적용하면
**μ42.8 σ16.0 범위 1~92 → μ70.8 σ5.2 범위 57~87** (47점 미만 0건).
MAE는 19.5→7.1로 좋아지지만, **교사 평균만 무조건 찍어도 MAE 8.2** — 개선폭 13%.
즉 변별력을 죽이고 전부 평균으로 밀어 넣는 값 조작이고, 히든젬 판별이라는 목적을 정면으로 부순다.

원인은 모델이 아니라 **검증 데이터의 범위 제한**이다. 교사가 채점한 4,190개는 인기작
위주로 gem 40~95(90%가 65+)에 몰려 있고, 신작이 사는 무명작 구간에는 교사 기준 자체가
없다. 홀드아웃을 늘려도 못 고친다(교사 풀에 50점 미만이 2%).
→ `calibrate_student`에 퇴화 매핑 거부 가드 3개를 넣어 이런 보정이 **자동으로 거부**되게 했다.
   (기울기<0.7 / 보정 후 MAE가 나빠짐 / 상수 예측 대비 개선 15% 미만)
   같은 가드로 9개 지표는 소폭 보정이 채택된다(평균 MAE 0.95 → 0.77).

## 3. 해결: gem을 추정에서 관측으로

뱃지 툴팁이 이미 정의를 갖고 있다 — "숨은 명작 지수 · **인지도 대비 품질**". 두 축 모두
Steam에서 측정 가능한데 LLM에게 4개 필드 설명만 주고 추측시키고 있었다.

```
품질   = 긍정 비율의 Wilson 하한(z=1.28)   # 표본 작으면 자동으로 보수적
무명도 = 1 − log1p(리뷰수)/log1p(CAP)      # CAP(기본 2만) 이상은 0
지수   = 100 × 품질 × 무명도^EXP           # 곱 = "좋고 + 덜 알려진" 것만 높게
```

교사/학생 같은 공식 → 12,837건이 하나의 스케일. `gem_potential`(LLM)은 **덮지 않고 보존**.

## 4. 적용하면 무엇이 달라지는가 (괴리)

`gem_evidence` 미리보기가 아래를 전부 숫자로 출력한다. 적용 전에 이걸 먼저 읽는다.

- 코호트별 현재 gem_percentile → 근거 지수 평균 변화, |Δ|>20 게임 수
- 뱃지(70+) **유지 / 신규 획득 / 상실** 건수 + 상실·신규 상위 10건 이름
- 표시 점수의 gem 보너스(최대 +5) 평균·σ 변화 (현재 / 전환 후 / review_bonus 제거 후)
- 근거 없는 게임 수와 그중 노출 중인 수

예상되는 방향과 그 판단:

| 변화 | 방향 | 판단 |
|---|---|---|
| 유명작(리뷰 2만+) 뱃지 상실, gem→0 | 의도한 것 | 히든젬 정체성과 일치. `max_review_count` 하드 필터가 하던 일을 점수 체계가 스스로 함 |
| 교사 코호트 평균 하락 | 큼 | 기존 4,190개는 인기작 위주라 정의상 히든젬이 아니다. 다만 **추천 순위가 전부 바뀌므로** 5장 회귀 비교 필수 |
| 리뷰 적고 평가 좋은 신작 상승 | 의도한 것 | 이번 수집의 목적 |
| 리뷰 0~9 신작은 지수 ≈ 0 | **구조적 한계** | 갓 나온 게임은 근거가 없어 히든젬이 될 수 없다. 노출 게이트와 30일 재평가(`--recheck`)가 이를 흡수. 발견 서비스로서 "신작" 동선은 gem이 아니라 출시일 기준으로 따로 두는 것이 맞다 |

## 5. 안전 적용 절차 (순서 고정)

1. **리뷰 조회 완료 확인** — `refresh_reviews --new` 가 끝나야 근거가 생긴다.
2. **회귀 스냅샷 (before)** — 실제 추천 결과를 저장한다. 분포가 아니라 결과를 본다.
   ```
   docker compose exec batch python -m embeddings.rec_snapshot --save before
   ```
   시나리오 13개: 취향 프리셋 5개 × (전체/히든젬), 시맨틱 검색 3개, 참조 게임 3개.
3. **괴리 미리보기** — DB 미변경. 파라미터를 바꿔가며 분포·뱃지 변동·보너스 영향을 확인.
   ```
   docker compose exec batch python -m embeddings.gem_evidence
   docker compose exec batch python -m embeddings.gem_evidence --obscurity-exp 1.0
   docker compose exec batch python -m embeddings.gem_evidence --confidence 95
   ```
4. **적용** — 원점수를 쓰고, 근거 없는 게임은 0으로 통일(한 컬럼에 두 기준이 섞이는 것 방지).
   ```
   docker compose exec batch python -m embeddings.gem_evidence --apply --yes
   ```
5. **review_bonus 이중 계상 제거** — `score_v6._gem_bonus` 가 gem_percentile 에
   `0.3 × (1 − 리뷰/1000)` 을 따로 더한다. 근거 지수에 무명도가 이미 들어있어 리뷰 수가
   두 번 반영된다. 3장 공식 전환과 **같은 커밋에서** 이 항을 제거해야 한다.
   (미리보기가 제거 전/후 보너스 평균·σ를 함께 보여준다.)
6. **회귀 스냅샷 (after) + diff**
   ```
   docker compose exec batch python -m embeddings.rec_snapshot --save after
   docker compose exec batch python -m embeddings.rec_snapshot --diff before after
   ```
   합격 기준: 히든젬 시나리오에서 유명작이 빠지고 무명작이 들어온다(의도), 취향
   시나리오(힐링/전략/서사/액션/공포)의 상위 10은 **절반 이상 유지**된다. 취향 결과가
   통째로 뒤집히면 gem 보너스가 매칭을 압도하는 것 → 보너스 비중 재검토.
7. **롤백 경로** — `recalc_percentile --yes` 한 줄로 LLM gem 기준 백분위로 복귀
   (gem_potential 원본이 보존되어 있어 결정적으로 재생성된다). 5장 코드 변경은 커밋 revert.

## 6. 앞으로 뽑을 데이터의 품질 보장

- **드리프트 게이트 (신규)**: `weekly_pipeline --audit-n 30` — 루프 종료 후 교사 게임 30개를
  학생 모델로 재분석해 `data/audit/quality_baseline.json`(오늘 값: 49지표 평균 MAE 0.77)과
  대조한다. 평균 MAE가 기준선의 1.3배를 넘으면 `audit_student` 가 exit 3 → Discord 알림 후
  중단. 모델·few-shot·프롬프트가 조용히 바뀌어 품질이 내려가는 것을 잡는 장치. 회당 약 $0.2.
  주간 스케줄에 이 옵션을 붙여 등록한다.
- **신뢰 못 할 3개 지표**: 추천 의도 가중치에서 Primary/Secondary 승격 금지(Irrelevant 취급).
  49개 중 3개, 오차 기여 25.4% → 빼면 벡터 거리 오차 14% 감소. 코드 변경은 5장과 함께.
- **gem_potential 의 위치 재정의**: 뱃지·보너스의 근거가 아니라 **근거가 아직 없는 게임의
  참고값**으로만 둔다. 프롬프트에서 제거하지는 않는다(교사와 스키마 동일성 유지 = few-shot
  증류의 전제).
- **노출 게이트 유지**: 리뷰 10개 미만은 분석·임베딩은 하되 비노출, 30일 주기 재평가로
  리뷰가 붙으면 자동 편입. 데이터는 지우지 않는다.
- **비용 가드**: `usage_report` 로 실사용량 기준 보고, `.env` 에 단가 등록 후에만 달러 추정 표시,
  `STOP_BACKFILL` 파일로 언제든 무과금 중단.

## 7. 미결정 (님 판단 필요)

1. `--obscurity-exp` 값: 0.5(권장) / 1.0(무명도 강조) — 미리보기 분포 보고 결정.
2. `--confidence` 90 / 95 — 95는 리뷰 10~20개 게임을 더 보수적으로 깎는다.
3. 뱃지 최소 리뷰 수: 리뷰 10개 100%가 지수 74.8로 뱃지를 받는다. 지인 리뷰 위험이
   걱정되면 뱃지에만 별도 하한(예: 30개)을 두는 방안.
4. 5장 `score_v6` 수정(review_bonus 제거 + 3개 지표 강등)은 추천 점수 체계를 건드리므로
   승인 후 진행.

## 8. 비용: 동기+캐시 실측 (2026-09-04, 홀드아웃 150건)

홀드아웃을 일부러 `--sync` 로 돌려 프롬프트 캐시가 실제로 붙는지 확인했다.

```
동기 호출 150건: 입력 3.98M 중 캐시 적중 3.75M (94.3%), 출력 0.24M
요청당 입력 26,516 / 그중 캐시 25,016 / 출력 1,591
```

few-shot 12개가 매 요청 접두부로 반복되므로 캐시 적중률이 94%까지 올라간다.
배치는 50% 할인이지만 **캐시 할인과 중복 적용되지 않는다** → 반복되는 25k 토큰을
매번 반값으로 전액 지불한다. 동기는 그 25k를 10%만 낸다(출력은 배치의 2배).

배치 실단가 $0.0071/요청(실측)에서 역산하면 동기+캐시는 요청당 약 **$0.0045 (배치의 64%)**.
남은 5,500건 기준 **배치 $39 vs 동기 $25**. 품질은 동일하다 — 같은 모델, 같은 프롬프트,
같은 few-shot 12개이고 캐시는 과금 방식만 바꾼다.

확정 방법: 홀드아웃 실행 전후 OpenAI Usage 일별 금액 차이 ÷ 150 = 동기 요청당 실단가.
이 값이 $0.0071 미만이면 재개는 `--sync` 로 한다.
